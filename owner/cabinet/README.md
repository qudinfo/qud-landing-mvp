## Поддержка: подготовленный интерфейс и серверный контракт

Кабинет запрашивает только защищённый `/owner/api/support` с Owner-сессией:

- `GET` возвращает `{ok, owner_id, owner_email, unread_count, messages}`;
- `POST` принимает только `{message}` и возвращает подтверждение отправки;
- `POST /owner/api/support/read` принимает `{message_id}` и отмечает ответ QUD
  прочитанным только у владельца текущей сессии.

Сообщение содержит `id`, `direction` (`owner` или `qud`), `body`, `created_at`
и `read_at`. Кнопка показывает число непрочитанных ответов; раскрытие ответа
отмечает его прочитанным. Интерфейс обновляет состояние раз в минуту при
открытой вкладке. Ввод и отправка доступны только при подтверждённом email,
полученном от защищённого API. Клиент не передаёт в `POST` Owner ID или email;
их должен определить сервер по сессии и будущему реестру владельцев.

Текущий Owner API не содержит маршрута поддержки, реестра email и данных
переписки. Поэтому реальная отправка, получение писем и синхронизация истории
пока не работают. Для запуска потребуется отдельный защищённый серверный
контур: проверка Owner-сессии, хранение истории по Owner ID в Google Таблице,
отправка на `infoqud@gmail.com` с указанием Owner ID и email владельца,
ответ сотрудника из этого Gmail на адрес владельца и периодическая
синхронизация ответов Gmail в ту же историю. У владельца не должно быть
маршрута удаления истории; очистка — только административное действие QUD.
Браузер не должен обращаться к Google Таблице или Gmail напрямую.

Под карточкой «Мои брокерские счета» добавлена кнопка создания до трёх
демонстрационных счетов. Каждый новый счёт занимает отдельную раскрываемую
строку. После третьего добавления кнопка исчезает; редактирование ранее
добавленного счёта не предусмотрено. Модальное окно запрашивает брокера, номер счёта и
скрытое поле мастер-пароля, показывает уведомление о конфиденциальности и
отдельное предупреждение не вводить действующий пароль в прототипе. В тестовом
режиме счета появляются в карточке без стратегии. Брокер, номер и пароль
существуют только в памяти открытой
авторизованной вкладки и удаляются при выходе, повторной проверке сессии или
обновлении страницы. В карточке пароль изначально замаскирован; кнопка с
иконкой глаза показывает его только по нажатию и скрывает повторно. Он также
скрывается при закрытии карточки, смене раздела или уходе с вкладки. При
раскрытии значение временно отображается на странице; локальное хранилище и
сеть не используются. Из-за отсутствия
защищённого API тестовые счета не помечаются подключёнными, но доступны
для предварительного выбора в форме заявки с явной отметкой «тестовый счёт».
Отправка заявки остаётся отключённой. Реальный приём секрета,
управление доступом и связь с аккаунтом владельца требуют отдельного
согласованного серверного контракта.

В раскрытой карточке две постоянные колонки: слева реквизиты брокера (брокер,
номер счёта, мастер-пароль), справа сведения о стратегии (состояние,
стратегия, дата подключения). На мобильной ширине порядок внутри колонок
сохраняется.

Отдельный крупный блок WebTerminal удалён после уточнения макета. Под новой
заявкой в правой колонке размещены подпись «Сделки на графике», ссылка
WebTerminal с иконкой глобуса на https://web.metatrader.app/terminal и
раскрываемая инструкция по входу с номером счёта, сервером брокера и
инвесторским паролем. Пароль не вводится и не сохраняется в QUD. Если общий
терминал не поддерживает сервер брокера, пользователь должен открыть терминал
на сайте брокера.

Инструкция «Как подать заявку» теперь раскрывается компактным всплывающим
окном поверх соседних блоков, визуально и по поведению как инструкция
WebTerminal; раскрытие не меняет высоту колонки заявки.

Иконка счёта в верхней панели увеличена и стоит слева от двух выровненных
строк «Owner Cabinet» и «Брокерский счёт». Карточка брокерских счетов теперь
содержит компактную раскрываемую строку на каждый счёт: в закрытом состоянии
видны название и стрелка; при раскрытии — номер заявки, статус, реквизиты
счёта и сведения о подключённой стратегии. Разметка рассчитана на несколько
независимых строк в одной карточке.
Пока серверный список счетов не подключён, до добавления тестового счёта
показана одна строка-заготовка без вымышленных номеров и стратегий.
Подключение реальных данных и жизненный цикл счетов требуют отдельного
согласованного API-контракта.

Над карточкой оставлена только подпись «Мои брокерские счета»; повторный
крупный заголовок удалён. Под списком счетов слева находится раскрываемый
блок рекомендуемых брокеров; подпись «Выбор брокера» вынесена над ним, за
пределы карточки. Справа — новая заявка без карточки: кнопка,
инструкция и компактная подпись «Новое подключение к стратегии». Её верхний
край выровнен с верхом карточки счёта. На экранах до 960 px порядок блоков:
счета, новая заявка с WebTerminal, затем выбор брокера.

Окно «Новая заявка» теперь содержит форму сервисного обслуживания. Стратегии
загружаются через существующий защищённый `GET /owner/api/strategies`; период
выбирается из 1 или 3 месяцев, предел риска — из 1–5%, а инструменты — из двух
наборов с раскрываемыми пояснениями. Перечень majors пока предварительный и
не обозначен как окончательно утверждённый QUD. Если в данных стратегии появится подтверждённая
категория `Elite`, форма автоматически ставит 3 месяца и блокирует 1 месяц.
Текущий публичный API категорию стратегии не отдаёт, поэтому правило пока
не может сработать на реальных данных. Выпадающий список счетов собирается из
строк блока «Мои брокерские счета», помеченных `data-connected="true"` и имеющих
`data-account-id`, `data-broker`, `data-server`, `data-account-number`. Текущая
строка-заготовка не является счётом. Добавленные демонстрационные счета также
появляются в списке с отметкой «тестовый счёт», но не считаются подключёнными
и не позволяют отправить заявку. Это только UI-контракт; будущая отправка должна повторно проверять
принадлежность счёта владельцу на сервере.

Под формой расположен предварительный расчёт. Его единственный источник —
опубликованные тарифные строки внутри `#broker-tariffs` с атрибутами
`data-service-tariff`, `data-period-months`, `data-strategy-category` (`all` для
общего тарифа) и `data-price-rub` (полная стоимость периода в рублях).
Выбранные стратегия и период определяют подходящую строку; точный тариф
категории имеет приоритет над общим. Сейчас блок «Тарифы» не содержит
утверждённых сумм, поэтому форма показывает отсутствие расчёта и не подставляет
вымышленные цены или скидки. Контракта отправки заявки пока нет: кнопка
отключена, данные никуда не отправляются.

# Этап 7 — Owner Login, 10.09.2026

Текущий frontend использует только GET / POST / DELETE `/owner/api/session`.
POST передаёт `{access_key: ...}`. Cookie устанавливает существующий Worker;
ключ не сохраняется frontend в localStorage или sessionStorage.
`session.js` управляет загрузкой, формой, открытием исходного shell и выходом.
Показатели исходного shell остаются демонстрационными.

Локально проверено в браузере с неизменённым owner-api.js и тестовым ключом:
- Access → кабинет → неверный ключ → корректный вход → shell → logout → форма;
- полноэкранная загрузка, сохранение cookie после перезагрузки;
- недействительная сессия → форма входа;
- недоступный API → ошибка → повторная проверка.
Проверка синтаксиса app.js и session.js успешна.

Публикация не выполнялась. Production PASS ещё не подтверждён.
Для публикации cabinet/index.html, app.js, styles.css и session.js должны
находиться в /owner/cabinet/. На опубликованной Access-странице заменить
только адрес кнопки «Уже есть доступ» на /owner/cabinet/.
Локальная access/index.html отличается от опубликованной версии: исходная
кнопка не имела ссылки. Не заменять публичную страницу целиком без сверки.
Backend, Apps Script, VP и sources не изменялись.

# QUD Owner Cabinet MVP

This directory contains the isolated frontend shell for the capital owner's cabinet.

Current route:

- `/owner/cabinet/`

Current stage:

- responsive frontend shell based on the approved dashboard composition;
- matte graphite visual system aligned with `/owner/access/` and
  `/traders/tradermap/`: flat dark surfaces, restrained grey accents and no
  gold glow effects;
- five primary sections: Overview, Strategies, Virtual Portfolio, Real Account and Documents;
- a Strategy Library with compact horizontal demo cards showing Strategy ID,
  Trust Score, Trust Zone, Win Ratio and history length;
- accessible inline expansion for one strategy at a time: the demo Balance
  chart follows the summary row, then only non-repeating additional KPIs;
- separate profile and logout controls;
- demo-only portfolio values marked in the interface and in the HTML with `data-demo`;
- no production user identity, subscription state or working financial data;
- no API calls, authentication or persistence in `app.js`;
- the existing Virtual Portfolio remains available at `/portal/portfolio/mvp/` and is not modified.

The Real Account, documents, help, profile and subscription controls are visual
placeholders. They must not be connected to production behavior until their
individual user flows and contracts are approved.

The profile displays `owner_id` and the access indicator accepts
